# Go Template

A starting point for Go HTTP services on Postgres, with a background worker, and the standards
already in place: code style, errors, logging, testing, database workflow, jobs, Docker and CI. One
small example feature (tasks, with a clean-up job) shows each of them in real code; copy its shape
for your first feature, then remove it.

## What's inside

| Path | What |
|---|---|
| `cmd/api` | the HTTP server: settings, Postgres pool, timeouts, clean shutdown on SIGTERM |
| `cmd/worker` | the job runner and scheduler, with [asynq](https://github.com/hibiken/asynq) on Valkey (Redis) |
| `internal/api` | routes, one JSON log line per request, [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) error replies, JSON body reading |
| `internal/apperr` | the kinds of expected failure services return (bad request, invalid, not found, conflict) |
| `internal/task` | the example feature's rules |
| `internal/jobs` | each background job's name, payload and options, shared by the API and the worker |
| `internal/worker` | job handlers, one JSON log line per job, retries, the schedule |
| `internal/startup` | what both commands do first: logger, Postgres and Valkey connections |
| `internal/db` | Go generated by [sqlc](https://sqlc.dev) from `db/queries` |
| `internal/testdb` | a fresh, migrated Postgres database per test |
| `internal/testqueue` | a Valkey connection for tests, on a database the app never uses |
| `internal/config` | settings from the environment, all problems reported at once |
| `db/` | `schema.sql` (edit this), migrations written by [Atlas](https://atlasgo.io), queries |
| `docs/standards/` | the rules, with reasons: [code style](docs/standards/code-style.md), [errors](docs/standards/errors.md), [logging](docs/standards/logging.md), [testing](docs/standards/testing.md), [HTTP API](docs/standards/http-api.md), [database](docs/standards/database.md), [jobs](docs/standards/worker.md) |
| `AGENTS.md` | the same rules in short, for AI coding tools (`CLAUDE.md` loads it) |
| `tools/go.mod` | pinned versions of golangci-lint, sqlc and govulncheck, kept out of the app's `go.mod` |
| `Dockerfile` | the API and worker images, and a `migrate` image that applies migrations |
| `.github/workflows` | CI: generated files up to date, lint, vulnerabilities, tests on Postgres and Valkey, images build |

## Prerequisites

- Go 1.21 or newer (`make` downloads the exact version in `go.mod`)
- Docker
- Atlas, Community edition: `brew install atlas` (Homebrew's build is the Apache-2.0 Community
  one; `atlas version` says "community")

## Start a project

1. On GitHub, **Use this template → Create a new repository**, then clone it. (Or clone this
   repository and run `rm -rf .git && git init`.) Don't use `gonew`: it leaves out `tools/`, which
   has its own `go.mod`.
2. Rename the module, then commit:

   ```sh
   make rename module=github.com/you/billing
   ```

   It changes both `go.mod` files, every Go import, the linter's import grouping and the image name.
   Update this README's title and links by hand.
3. Run it locally:

   ```sh
   cp .example.env .env
   make db-up           # Postgres 17 and Valkey 8 in Docker
   make migrate-apply
   make run             # http://localhost:8080/healthz
   make run-worker      # in another terminal
   ```

   If another Postgres already uses port 5432, change `POSTGRES_PORT` and the port in
   `DATABASE_URL` and `TEST_DATABASE_URL` in `.env`; for another Redis on 6379, `VALKEY_PORT` and
   the port in `REDIS_URL` and `TEST_REDIS_URL`.

## Everyday commands

| Command | What |
|---|---|
| `make run` / `make run-worker` | run the API / the worker |
| `make test` | start Postgres and Valkey, run every test with the race detector in random order |
| `make fmt` / `make lint` | format / lint (CI fails on any lint issue) |
| `make migrate-diff name=<what_changed>` | write a migration from your `db/schema.sql` edit |
| `make generate` | regenerate `internal/db` from `db/queries` |
| `make migrate-apply` | apply migrations to `DATABASE_URL` |
| `make check-generated` | fail if generated code, `atlas.sum` or migrations are out of date |
| `make vuln` | known vulnerabilities in dependencies |
| `make image` | build the API, worker and migrate images |
| `make test-db-clean` | drop databases that failed tests kept for inspection |

Before you push: `make fmt lint test check-generated`. The database workflow is in
[docs/standards/database.md](docs/standards/database.md).

## Replacing the example

Build your first feature the way tasks are built (service in `internal/<feature>`, routes in
`internal/api/<feature>.go`, jobs in `internal/jobs/<feature>.go` and `internal/worker/<feature>.go`,
tests next to each), then remove tasks.
sqlc needs at least one query, so do it in one go with your first table:

1. Delete the example:

   ```sh
   rm -r internal/task internal/api/tasks.go internal/api/tasks_test.go \
     internal/jobs/tasks.go internal/worker/tasks.go internal/worker/tasks_test.go \
     db/queries/tasks.sql db/migrations internal/db/tasks.sql.go
   ```

2. In `db/schema.sql`, replace the `tasks` table and index with your own table; put its queries in
   `db/queries/<feature>.sql`.
3. Replace tasks with your own feature in `internal/api/router.go` (the `Tasks` field of
   `api.Services`, its line in `NewServices`, the `taskRoutes{...}.mount(router)` line) and in
   `internal/worker/worker.go` (the same three in `worker.Services`, `NewServices` and `NewMux`,
   and the `scheduleTaskJobs` call in `newScheduler`).
4. Regenerate and check:

   ```sh
   make migrate-diff name=init   # a fresh first migration for your schema
   make generate
   make fmt lint test check-generated
   ```

   `make lint` then reports any shared helper no feature uses any more as `unused` (for example
   `cursorOf` and `defaultPageSize` if nothing has a paged list yet, `jobResponse` if no endpoint
   queues a job): delete those, and run it again.

## Deploying

Build the images with `make image` (on an arm64 Mac, for amd64 servers:
`docker build --platform linux/amd64 ...`). Each release:

1. Run the migrate image once, with the database's `DATABASE_URL`:
   `docker run --rm -e DATABASE_URL=... <name>-migrate`. Migrations must work with the app
   version still running ([why](docs/standards/database.md#migrations-that-are-safe-while-the-old-app-runs)).
2. Start the new API and worker images with their settings in the environment (both read the same
   ones; `.example.env` lists them, and `APP_ENV` defaults to `production`). There is no `.env` in
   the images.
3. Point the platform's health check at `GET /healthz` on port 8080. The image has no shell, so a
   Docker `HEALTHCHECK` can't run inside it.

The API stops cleanly on SIGTERM: it refuses new requests, gives running ones up to 15 s, then
closes whatever is left and exits. The worker gives running jobs 8 s and puts the unfinished ones
back in the queue ([worker.md](docs/standards/worker.md#time-limits-and-shutdown)).
