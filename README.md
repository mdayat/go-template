# Go Template

A starting point for Go services on Postgres, with the standards already in place: code style,
errors, logging, testing, database workflow, calling outside services, Docker and CI. One small
example feature (tasks) shows each of them in real code; copy its shape for your first feature,
then remove it.

<!-- remove:template -->
It comes with two programs, an HTTP API and a background worker that runs queued and scheduled
jobs. Keep both, one or neither: see [Choose what you need](#choose-what-you-need).

<!-- remove:end -->

| `AGENTS.md` | the same rules in short, for AI coding tools (`CLAUDE.md` loads it) |
| `tools/go.mod` | pinned versions of golangci-lint, sqlc and govulncheck, kept out of the app's `go.mod` |
| `Dockerfile` | each program's image, and a `migrate` image that applies migrations |
| `.github/workflows` | CI: generated files up to date, versions agree, lint, vulnerabilities, tests, images build |
| `.github/dependabot.yml` | pull requests for newer dependencies, when you ask (and once a quarter) |

### The HTTP API

| Path | What |
|---|---|
| `cmd/api` | the HTTP server: settings, Postgres pool, timeouts, clean shutdown on SIGTERM |
| `internal/api` | routes per client (`mobile/` at `/mobile/v1`, `web/` at `/web`, `admin/` at `/admin`; helpers they share in `handler/`), one JSON log line per request, [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) error replies, JSON body reading, sign-in and [rate limits](docs/standards/http-api.md#rate-limits) on every route but the health and readiness checks |
| `internal/auth` | who signed in, as a provider proved it; `internal/auth/jwks` checks JWTs against the issuer's published keys (Firebase, Auth0, Cognito, Keycloak, Supabase; see [signing in](docs/standards/http-api.md#signing-in)) |
| `internal/ratelimit` | counting requests for the rate limits: in Valkey (`internal/ratelimit/valkey`), shared by every copy of the API, or in memory |
| `internal/authtest`, `scripts/devtoken` | a stand-in sign-in provider: for tests, and for local runs (`make dev-token`) |
| `docs/standards/http-api.md` | [the HTTP API's rules](docs/standards/http-api.md) |

## Prerequisites

- Go 1.21 or newer (`make` downloads the exact version in `go.mod`)
- Docker
- Atlas, Community edition: `brew install atlas` (Homebrew's build is the Apache-2.0 Community
  one; `atlas version` says "community")

## Start a project

1. On GitHub, **Use this template → Create a new repository**, then clone it. (Or clone this
   repository and run `rm -rf .git && git init`.) Don't use `gonew`: it leaves out `tools/`, which
   has its own `go.mod`.
2. Rename the module, then commit:

   ```sh
   make rename module=github.com/you/billing
   ```

   It changes both `go.mod` files, every Go import, the linter's import grouping and the image name.
   Update this README's title and links by hand.
3. Run it locally:

   ```sh
   cp .example.env .env
   make db-up           # the services in compose.yaml, in Docker
   make migrate-apply
   ```

   If another Postgres already uses port 5432, change `POSTGRES_PORT` and the port in
   `DATABASE_URL` and `TEST_DATABASE_URL` in `.env`.
   <!-- remove:api -->
   - Run `make dev-token user=alice` once: it makes the local sign-in key the API needs, and prints
     a token. Start the API with `make run`, then open http://localhost:8080/healthz; every route
     but it and `/readyz` needs `Authorization: Bearer <token>`.
   <!-- remove:end -->
   <!-- remove:valkey -->
   If another Redis already uses port 6379, change `VALKEY_PORT` and the port in `REDIS_URL` and
   `TEST_REDIS_URL` in `.env`.
   <!-- remove:end -->
   <!-- remove:worker -->
   - Start the worker with `make run-worker` (in another terminal).
   <!-- remove:end -->

## Everyday commands

| Command | What |
|---|---|
| `make test` | start the compose services, run every test with the race detector in random order |
| `make fmt` / `make lint` | format / lint (CI fails on any lint issue) |

| `make vuln` | known vulnerabilities in dependencies |

### Keeping dependencies up to date

Run Dependabot when you want updates: on GitHub, **Insights → Dependency graph → Dependabot →
Check for updates** (it also runs once a quarter, in case nobody does, and every week for the
Dockerfile's base images: they're pinned by digest, so a security fix to one arrives only this
way). Each run opens at most four pull requests, one each for Go modules (the app's and the
tools'), GitHub Actions, the Dockerfile's base images and the local Prometheus, Jaeger and Grafana
in `compose.yaml`; merge each once CI passes (CI doesn't start those three: try theirs with `make
telemetry-up` first), or close it to skip. When one update in a pull request breaks CI (a new lint
rule, a changed API), fix the code in that pull request, or add the dependency to `ignore` in
`.github/dependabot.yml` and check for updates again. Known security holes don't wait for
Dependabot: `make vuln` (the Go code) and `make scan` (the images' system packages), in CI, fail on
them. Two versions are changed by hand, everywhere at once (`make check-versions`, run
by CI, fails until they agree):

- **Go:** the `go` line in `go.mod` and `tools/go.mod`, and the Dockerfile's `golang` image.
  Dependabot's pull request for a newer `golang` image is the reminder; `make vuln` also reports
  a known hole in the Go version in use.
- **Atlas:** the Dockerfile's `arigaio/atlas` image (its tag and digest), and `ATLAS_VERSION`
  with `ATLAS_SHA256` in `.github/workflows/code_quality_checks.yaml` (the checksum of the file CI
  downloads, from `shasum -a 256`).

Trivy, which `make scan` runs, is pinned only in CI's install step: change `TRIVY_VERSION` and
`TRIVY_SHA256` together, with the checksum from the release's `checksums.txt`. Its list of known
holes changes daily, so `make scan` can fail with no change of yours: update the image it names
(Dependabot's base-image pull request, or Atlas by hand). A hole that doesn't affect you, or that
waits on an image you can't update yet, goes in a `.trivyignore` file, its ID with a comment
saying why.

## Replacing the example

Build your first feature the way tasks are built (its service in `internal/<feature>`, with its
tests), then remove tasks, in one go with your first table:

1. Delete the example:

   ```sh
   rm -r internal/task db/queries/tasks.sql db/migrations internal/db/tasks.sql.go
   ```

   <!-- remove:api -->
   - The API's part: `rm internal/api/mobile/tasks.go internal/api/web/tasks.go
     internal/api/tasks_test.go`. Replace tasks with your feature in `internal/api/router.go`: the
     `Tasks` field of `api.Services`, its line in `NewServices`, and the `mobile.Tasks{...}` and
     `web.Tasks{...}` lines in `NewRouter`. Keep `internal/api/handler` (paging and path IDs
     included): your feature's handlers use it. Two tests of the router itself call the example's
     routes: point `TestClientPrefixes` (`router_test.go`) and `limitedRoute`
     (`ratelimit_test.go`) at yours.
   <!-- remove:end -->
   <!-- remove:worker -->
   - The worker's part: replace tasks with your feature in `internal/worker/worker.go` (the `Tasks`
     field of `worker.Services` and its line in `NewServices`) and in `tablePurges`
     (`internal/worker/purge.go`), whose purge every soft-deleted table needs. The purge's tests
     (`internal/worker/purge_test.go`) seed tasks: seed your table instead.
   <!-- remove:end -->
   - The example one-off command: `rm internal/oneoff/trim_task_titles.go
     internal/oneoff/trim_task_titles_test.go`, and its line in `Commands()`
     (`internal/oneoff/commands.go`).
2. In `db/schema.sql`, replace the `tasks` table and indexes with your own table; put its queries in
   `db/queries/<feature>.sql`. In `sqlc.yaml`, replace `tasks` with your table in the soft-delete
   rule's list (or empty the list if nothing is soft deleted).
3. Regenerate and check:

   ```sh
   make migrate-diff name=init   # a fresh first migration for your schema
   make generate
   make fmt lint test check-generated
   ```

   `make lint` then reports any unexported shared helper no feature uses any more as `unused`:
   delete those, and run it again.

## Choose what you need

The template has two programs, and either can go. Commit first: `make remove` changes only files
git sees, so `git restore . && git clean -fd` undoes it.

| You want | Run | What goes |
|---|---|---|
| the HTTP API only | `make remove what=worker` | the worker and the whole job queue (asynq), the purge endpoint |
| the worker only | `make remove what=api` | the API and its settings (`HTTP_ADDR`, sign-in, rate limits) |
| neither: a program of your own | both of the above | both, and Valkey (`REDIS_URL`), which only they use; leaving the shared core and every standard's example |
| both | `make remove what=markers` | only the `remove:` comments in the files, and the remove tool |

Each removal deletes the part's folders and the lines marked for it in shared files, then
formats, tidies `go.mod`, builds, and checks that no file still mentions the part. Your own `.env`
is never edited (git ignores it): delete the removed part's settings from it by hand. CI then
checks only the shape you chose.

## A program of your own

A new program goes in `cmd/<name>/`: a `main.go`, and a `settings.go` (with its test) that reads
its settings through `internal/config`. Its `main` takes these steps, in this order (a summary
to follow, not code that's checked):

1. Make a context that ends on SIGINT or SIGTERM (`signal.NotifyContext`).
2. Load `.env` (`config.Env()`) and read the settings; stop with every problem in one error.
3. Set up the logger (`startup.SetupLogger`) and Go's memory limit (`startup.LimitMemory`). A
   long-running program also serves profiles if asked (`startup.ServeProfiles`) and starts
   telemetry (`telemetry.Start`, `Flush` last on the way out); a short one passes no-op providers
   instead, as `cmd/oneoff` does.
4. Connect (`startup.ConnectDB`, with a [pool size](docs/standards/database.md#connections) and
   [time limits](docs/standards/database.md#time-limits) fit for its work, and the providers from
   step 3), closing each connection on the way out.
5. Do its work until the context ends, then stop within the time the platform gives between
   SIGTERM and a hard kill (Docker: 10 s by default; Kubernetes and ECS: 30 s).
6. Return errors to `main`, which logs the one that stopped it and exits 1.

Give it an image: a stage in the `Dockerfile` that copies its binary from the build stage (which
builds every program in `cmd/`), and an `image-<name>` target in the `Makefile`.

## Deploying

Build the images with `make image` (on an arm64 Mac, for amd64 servers:
`docker build --platform linux/amd64 ...`). Each release:

1. Run the migrate image once, with the database's `DATABASE_URL`:
   `docker run --rm -e DATABASE_URL=... <name>-migrate`. Migrations must work with the app
   version still running ([why](docs/standards/database.md#migrations-that-are-safe-while-the-old-app-runs)).
2. Run any one-off command the release needs with the oneoff image, a dry run first:
   `docker run --rm -e DATABASE_URL=... <name>-oneoff <command>`, then again with `--apply`
   ([commands.md](docs/standards/commands.md)).
3. Start each program's new image with its settings in the environment (`.example.env` lists them;
   each program's `settings.go` says which it reads, and `APP_ENV` defaults to `production`). There
   is no `.env` in the images.

In the long-running programs, metrics and traces are on (`cmd/oneoff` sends none), pushed to
`http://localhost:4318` unless set otherwise: point them at a collector (or your stores) with
`OTEL_EXPORTER_OTLP_ENDPOINT`, set `OTEL_METRICS_EXPORTER=prometheus` for a page to scrape, or set
either exporter to `none` ([metrics.md](docs/standards/metrics.md#where-they-go),
[tracing.md](docs/standards/tracing.md#where-they-go)). With nothing at the endpoint, each program
logs a warning once a minute. An empty setting counts as unset (on); `OTEL_SDK_DISABLED=true` turns
both off.

Profiles (where CPU and memory go) are off unless `PPROF_ADDR` is set, and then only on the
machine itself: reach them with a port forward ([profiles](docs/standards/metrics.md#profiles)).

Give each container a memory limit. Go doesn't read it by itself (it does read the CPU limit), so at
start each program sets Go's own limit (`GOMEMLIMIT`) to 90% of the container's: near it, Go frees
memory harder instead of the container killing the program for going past it. The start log shows
the value, and so does the `go.memory.limit` metric (absent when there's no limit).
`AUTOMEMLIMIT=0.8` changes the share, `AUTOMEMLIMIT=off` turns this off, and a `GOMEMLIMIT` you set
(`450MiB`) is kept as it is: set it in the environment, as Go reads it before `.env` is loaded (the
programs refuse one there). Without a container limit, or one that can't be read (a warning),
nothing changes.

<!-- remove:api -->
The API serves `GET /healthz` on port 8080: point the platform's restart check at it. Point the
load balancer's check at `GET /readyz`, which fails while the database doesn't answer and once the
API is shutting down ([server settings](docs/standards/http-api.md#server-settings)). The image has
no shell, so a Docker `HEALTHCHECK` can't run inside it. On SIGTERM the API keeps serving for
`SHUTDOWN_DELAY` (about `5s` behind a load balancer; unset, none), then refuses new requests, gives
running ones up to 8 s, closes whatever is left and exits.

Behind a load balancer or CDN, set `TRUSTED_PROXIES` to its IP ranges, or every signed-out client
shares one rate limit (the proxy's); see [rate limits](docs/standards/http-api.md#rate-limits).

Set `AUTH_JWKS_URL`, `AUTH_ISSUER` and `AUTH_AUDIENCE` to your sign-in provider's (an https://
keys URL that answers 200 itself, not a redirect; the API refuses anything else in production).
Each copy of the API fetches the keys at start (up to 5 s) and every hour; if the provider can't
be reached at start, the API still starts and answers 503 to signed-in routes until it has them
(it tries again when a token naming a key arrives, at most every 5 minutes, else at the hourly
fetch).

On SIGTERM the worker gives running jobs 8 s and puts the unfinished ones back in the queue

### Settings and secrets

The programs read settings only from the environment (and a local `.env`). Let the platform put
secrets there from your secret manager, and the code never needs to know which one you use:
Kubernetes External Secrets, ECS task definition `secrets` (AWS Secrets Manager or Parameter Store),
or `infisical run -- /<program>` (this needs the Infisical CLI in the image; the template's images
hold only the program). Changing secret manager then changes no code.

If the program must fetch its secrets itself (the platform can't fill the environment), fetch them
all once at startup into a `config.Map` (a `config.Source`), and pass it after `config.Env()` in
the program's `main.go`: `loadSettings(env, secrets)`. The environment then still
overrides a single value, and the source's own login (client ID, secret) comes from the environment.
Values fetched this way reach only the settings in `settings.go`, never the environment, so a
library that reads its own variable (pgx's `PGPASSWORD`, the AWS SDK's keys) won't see them: put a
database password in `DATABASE_URL`, and pass other libraries their values in code.

### Switching a feature off

To ship code before it's ready, put it behind an on/off setting read in `settings.go` like any
other, off unless set. Once the feature is on everywhere, delete the setting and the code for
"off": a switch left behind is a second path nobody tests. To switch per user, or without a
restart, use a feature-flag service, through [OpenFeature](https://openfeature.dev) (a standard Go
interface any such service plugs into), so changing service changes no code.
