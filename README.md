# Go Template

A starting point for Go services on Postgres, with the standards already in place: code style,
errors, logging, testing, database workflow, calling outside services, Docker and CI. One small
example feature (tasks) shows each of them in real code; copy its shape for your first feature,
then remove it.

<!-- remove:template -->
It comes with two programs, an HTTP API and a background worker that runs queued and scheduled
jobs. Keep both, one or neither: see [Choose what you need](#choose-what-you-need).

<!-- remove:end -->
## What's inside

| Path | What |
|---|---|
| `internal/apperr` | the kinds of expected failure services return (bad request, invalid, not found, conflict) |
| `internal/json` | the only package that imports a JSON library, so it can be replaced there alone |
| `internal/httpclient` | HTTP clients for outside services, each call with a time limit, and which failures are worth retrying |
| `internal/webhook` | reports events to a URL another system gave us (the example of calling an outside service) |
| `internal/task` | the example feature's rules, and their tests |
| `internal/postgres` | recognises the Postgres driver's errors, so services don't import the driver |
| `internal/startup` | what every program does first: the logger, the Postgres connection |
| `internal/db` | Go generated by [sqlc](https://sqlc.dev) from `db/queries` |
| `internal/testdb` | a fresh, migrated Postgres database per test |
| `internal/config` | reads settings from the environment and `.env` (or a secret manager you add), all problems reported at once; each program lists its own in `cmd/<name>/settings.go` |
| `db/` | `schema.sql` (edit this), migrations written by [Atlas](https://atlasgo.io), queries |
| `docs/standards/` | the rules, with reasons: [code style](docs/standards/code-style.md), [errors](docs/standards/errors.md), [logging](docs/standards/logging.md), [testing](docs/standards/testing.md), [database](docs/standards/database.md), [outside services](docs/standards/outside-calls.md) |
| `AGENTS.md` | the same rules in short, for AI coding tools (`CLAUDE.md` loads it) |
| `tools/go.mod` | pinned versions of golangci-lint, sqlc and govulncheck, kept out of the app's `go.mod` |
| `Dockerfile` | each program's image, and a `migrate` image that applies migrations |
| `.github/workflows` | CI: generated files up to date, lint, vulnerabilities, tests, images build |

## Prerequisites

- Go 1.21 or newer (`make` downloads the exact version in `go.mod`)
- Docker
- Atlas, Community edition: `brew install atlas` (Homebrew's build is the Apache-2.0 Community
  one; `atlas version` says "community")

## Start a project

1. On GitHub, **Use this template → Create a new repository**, then clone it. (Or clone this
   repository and run `rm -rf .git && git init`.) Don't use `gonew`: it leaves out `tools/`, which
   has its own `go.mod`.
2. Rename the module, then commit:

   ```sh
   make rename module=github.com/you/billing
   ```

   It changes both `go.mod` files, every Go import, the linter's import grouping and the image name.
   Update this README's title and links by hand.
3. Run it locally:

   ```sh
   cp .example.env .env
   make db-up           # the services in compose.yaml, in Docker
   make migrate-apply
   ```

   If another Postgres already uses port 5432, change `POSTGRES_PORT` and the port in
   `DATABASE_URL` and `TEST_DATABASE_URL` in `.env`.
   <!-- remove:api -->
   - Start the API with `make run`, then open http://localhost:8080/healthz.
   <!-- remove:end -->
   <!-- remove:worker -->
   - Start the worker with `make run-worker` (in another terminal). For another Redis on port
     6379, change `VALKEY_PORT` and the port in `REDIS_URL` and `TEST_REDIS_URL` in `.env`.
   <!-- remove:end -->

## Everyday commands

| Command | What |
|---|---|
| `make test` | start the compose services, run every test with the race detector in random order |
| `make fmt` / `make lint` | format / lint (CI fails on any lint issue) |
| `make migrate-diff name=<what_changed>` | write a migration from your `db/schema.sql` edit |
| `make generate` | regenerate `internal/db` from `db/queries` |
| `make migrate-apply` | apply migrations to `DATABASE_URL` |
| `make check-generated` | fail if generated code, `atlas.sum` or migrations are out of date |
| `make vuln` | known vulnerabilities in dependencies |
| `make image` | build each program's image and the migrate image |
| `make test-db-clean` | drop databases that failed tests kept for inspection |

- `make run`: run the API.

## Replacing the example

Build your first feature the way tasks are built (its service in `internal/<feature>`, with its
tests), then remove tasks. sqlc needs at least one query, so
do it in one go with your first table:

1. Delete the example:

   ```sh
   rm -r internal/task db/queries/tasks.sql db/migrations internal/db/tasks.sql.go
   ```

   <!-- remove:api -->
   - The API's part: `rm internal/api/tasks.go internal/api/tasks_test.go`. Replace tasks with your
     feature in `internal/api/router.go`: the `Tasks` field of `api.Services`, its line in
     `NewServices`, and the `taskRoutes{...}.mount(router)` line.
   <!-- remove:end -->
   <!-- remove:worker -->
   - The worker's part: `rm internal/jobs/tasks.go internal/worker/tasks.go
     internal/worker/tasks_test.go`. Replace tasks with your feature in `internal/worker/worker.go`:
     the `Tasks` and `PurgeReports` fields of `worker.Services`, their lines in `NewServices`, the
     `taskJobs{...}.mount(mux)` line in `NewMux`, and `taskSchedules` in `Schedules`. Drop the purge webhook from `cmd/worker` (`purgeReports`, and
     `PURGE_WEBHOOK_URL` in `settings.go` and `.example.env`).
   <!-- remove:end -->
2. In `db/schema.sql`, replace the `tasks` table and index with your own table; put its queries in
   `db/queries/<feature>.sql`.
3. Regenerate and check:

   ```sh
   make migrate-diff name=init   # a fresh first migration for your schema
   make generate
   make fmt lint test check-generated
   ```

   `make lint` then reports any shared helper no feature uses any more as `unused`: delete those,
   and run it again.

## Choose what you need

The template has two programs, and either can go. Commit first: `make remove` changes only files
git sees, so `git restore . && git clean -fd` undoes it.

| You want | Run | What goes |
|---|---|---|
| the HTTP API only | `make remove what=worker` | the worker and the whole job queue: Valkey, `REDIS_URL`, the purge endpoint |
| the worker only | `make remove what=api` | the API and its settings (`HTTP_ADDR`) |
| neither: a program of your own | both of the above | both, leaving the shared core and every standard's example |
| both | `make remove what=markers` | only the `remove:` comments in the files, and the remove tool |

Each removal deletes the part's folders and the lines marked for it in shared files, then
formats, tidies `go.mod`, builds, and checks that no file still mentions the part. Your own `.env`
is never edited (git ignores it): delete the removed part's settings from it by hand. CI then
checks only the shape you chose.

## A program of your own

A new program goes in `cmd/<name>/`: a `main.go`, and a `settings.go` (with its test) that reads
its settings through `internal/config`. Its `main` takes these steps, in this order (a summary
to follow, not code that's checked):

1. Make a context that ends on SIGINT or SIGTERM (`signal.NotifyContext`).
2. Load `.env` (`config.Env()`) and read the settings; stop with every problem in one error.
3. Set up the logger (`startup.SetupLogger`), then connect (`startup.ConnectDB`), closing each
   connection on the way out.
4. Do its work until the context ends, then stop within the time the platform gives between
   SIGTERM and a hard kill (Docker: 10 s by default; Kubernetes and ECS: 30 s).
5. Return errors to `main`, which logs the one that stopped it and exits 1.

Give it an image: a stage in the `Dockerfile` that copies its binary from the build stage (which
builds every program in `cmd/`), and an `image-<name>` target in the `Makefile`.

## Deploying

Build the images with `make image` (on an arm64 Mac, for amd64 servers:
`docker build --platform linux/amd64 ...`). Each release:

1. Run the migrate image once, with the database's `DATABASE_URL`:
   `docker run --rm -e DATABASE_URL=... <name>-migrate`. Migrations must work with the app
   version still running ([why](docs/standards/database.md#migrations-that-are-safe-while-the-old-app-runs)).
2. Start each program's new image with its settings in the environment (`.example.env` lists them;
   each program's `settings.go` says which it reads, and `APP_ENV` defaults to `production`). There
   is no `.env` in the images.

<!-- remove:api -->
The API serves `GET /healthz` on port 8080: point the platform's health check at it. The image
has no shell, so a Docker `HEALTHCHECK` can't run inside it. On SIGTERM the API refuses new
requests, gives running ones up to 15 s, then closes whatever is left and exits.

<!-- remove:end -->
<!-- remove:worker -->
On SIGTERM the worker gives running jobs 8 s and puts the unfinished ones back in the queue
([worker.md](docs/standards/worker.md#time-limits-and-shutdown)).

### Settings and secrets

The programs read settings only from the environment (and a local `.env`). Let the platform put
secrets there from your secret manager, and the code never needs to know which one you use:
Kubernetes External Secrets, ECS task definition `secrets` (AWS Secrets Manager or Parameter Store),
or `infisical run -- /<program>` (this needs the Infisical CLI in the image; the template's images
hold only the program). Changing secret manager then changes no code.

If the program must fetch its secrets itself (the platform can't fill the environment), fetch them
all once at startup into a `config.Map` (a `config.Source`), and pass it after `config.Env()` in
the program's `main.go`: `loadSettings(env, secrets)`. The environment then still
overrides a single value, and the source's own login (client ID, secret) comes from the environment.
Values fetched this way reach only the settings in `settings.go`, never the environment, so a
library that reads its own variable (pgx's `PGPASSWORD`, the AWS SDK's keys) won't see them: put a
database password in `DATABASE_URL`, and pass other libraries their values in code.
